---
title: "Pesquisa Dinâmica"
description: "A Pesquisa Dinâmica carrega opções de uma API remota em tempo real à medida que o enumerador digita, permitindo conjuntos de dados grandes ou frequentemente atualizados."
---

**Pesquisa Dinâmica** (também chamada de Search API) permite que um campo `select_one`, `select_multiple` ou `text` carregue suas opções de um serviço web remoto **em tempo de execução** à medida que o enumerador digita. Esta é a abordagem correta quando sua lista de opções é grande demais para ser incluída em um arquivo CSV, é atualizada frequentemente ou provém de um banco de dados em tempo real.

---

## Aparência `search-api()`

A pesquisa dinâmica é configurada através da coluna `appearance` utilizando a função `search-api()`:

```
search-api(method, url, post_body, value_column, display, data_path, save_path)
```

### Parâmetros

| Parâmetro | Descrição |
|-----------|-------------|
| `method` | Sempre use `'POST'` |
| `url` | O endpoint da API a ser consultado |
| `post_body` | Corpo JSON enviado para a API. Use `%__input__%` como um marcador de posição para o texto de pesquisa atual do enumerador |
| `value_column` | A chave no objeto de resposta a ser usada como o **valor** armazenado |
| `display` | A chave (ou modelo) a ser usada como o **rótulo** mostrado no menu suspenso. Suporta marcadores `##key##` e expressões `@{func}` |
| `data_path` | JSONPath para o array de objetos de resultado na resposta (ex: `$.data`, `$.hits.hits.*._source`) |
| `save_path` | Um nome sob o qual a resposta bruta é salva para uso por outros campos |

---

## Exemplo básico

Uma pesquisa de unidade de saúde onde o enumerador digita parte do nome da unidade:

| type | name | label | appearance |
|------|------|-------|------------|
| select_one | facility | Selecionar unidade de saúde | `search-api('POST', 'https://api.example.com/facilities/search', '{"query": "%__input__%"}', 'id', 'name', '$.results', 'facility_data')` |

A API recebe `{"query": "nair"}` quando o enumerador digita "nair" e retorna:

```json
{
  "results": [
    {"id": "HF001", "name": "Nairobi Central Clinic"},
    {"id": "HF002", "name": "Nairobi West Hospital"}
  ]
}
```

O menu suspenso mostra `Nairobi Central Clinic` e `Nairobi West Hospital`; o valor armazenado é `HF001` ou `HF002`.

## Formatação avançada de exibição

### Usando modelos `##key##`

Mostrar múltiplos campos no rótulo:

```
search-api('POST', 'https://api.example.com/search', '{"q": "%__input__%"}', 'id', '##name## (##district##)', '$.data', 'res')
```

Exibido como: `Nairobi Central Clinic (Nairobi)`.

### Usando expressões `@{func}`

Aplicar lógica condicional no rótulo de exibição:

```
search-api('POST', 'https://api.example.com/search', '{"q": "%__input__%"}', 'id',
  '@{if_else(eq("##status##", "active"), "✓ ##name##", "✗ ##name##")}',
  '$.data', 'res')
```

Resultados ativos mostram `✓ Clinic Name`; inativos mostram `✗ Clinic Name`.

---

## Definindo um valor padrão: `search-default-api()`

Use `search-default-api()` após `search-api()` para pré-preencher o campo com uma escolha padrão carregada de uma chamada de API separada (ex: ao editar um registro existente):

```
appearance: search-api(...) search-default-api('POST', 'https://api.example.com/get', '{"id": "##saved_id##"}', 'id', 'name', '$.item')
```

---

## Separador personalizado para select_multiple: `search-default-separator()`

Para campos `select_multiple`, especifique como múltiplos valores selecionados são unidos na string armazenada:

```
appearance: search-api(...) search-default-separator(' || ')
```

O separador padrão é um espaço.

## Tipos de pergunta suportados

| Tipo de pergunta | Caso de uso |
|---------------|----------|
| `select_one` | Seleção única a partir dos resultados da pesquisa |
| `select_multiple` | Múltiplas seleções a partir dos resultados da pesquisa |
| `text` | Autocompletar — o enumerador digita livremente, mas pode selecionar uma sugestão |

## Usando dados de resposta salvos

Quando o enumerador seleciona um resultado, o rtSurvey salva o objeto correspondente completo da resposta sob o nome `save_path`. Outros campos podem ler dele de duas maneiras.

### Método 1 — consulta `pulldata()`

Use `pulldata('save_path', 'key')` para ler um campo de nível superior do objeto salvo:

| type | name | label | calculation |
|------|------|-------|-------------|
| select_one | facility | Selecionar unidade | |
| calculate | facility_district | | `pulldata('facility_data', 'district')` |
| calculate | facility_type | | `pulldata('facility_data', 'type')` |
| calculate | facility_beds | | `pulldata('facility_data', 'beds')` |

A aparência na linha `select_one` deve incluir `search-api(..., 'facility_data')` com o `save_path` correspondente.

Para **campos JSON aninhados**, combine com `substr-jsonpath()`:

```
substr-jsonpath(pulldata('facility_data', 'location'), '$.district')
```

## Pesquisa em arquivo local com search()

`search()` realiza consultas offline de igualdade de colunas contra um arquivo SQLite `.db` incluído — sem conexão de rede e sem necessidade de consultas SQL. Use-o quando seus dados de referência estão empacotados com o formulário e você precisa de uma consulta simples de "encontrar todas as linhas onde a coluna é igual ao valor".

### Assinatura

```
search(path, 'matches', 'list_name', ${field})
```

### Parâmetros

| Parâmetro | Descrição |
|-----------|-------------|
| `path` | Caminho para a tabela SQLite: `concat(${family_path}, '/file.db::table')` |
| `'matches'` | Operador de correspondência — retorna linhas onde a coluna é igual ao valor |
| `'list_name'` | Nome da coluna para comparar |
| `${field}` | Valor a comparar; normalmente uma referência de campo |

### Exemplo

Preencher um `select_one` a partir de um banco de dados local, comparando o valor de `${d307}` com a coluna `list_name` na tabela `externalData` de `d307.db`:

| type | name | label | appearance |
|------|------|-------|------------|
| select_one | facility | Selecionar unidade | `search(concat(${family_path}, '/d307.db::externalData'), 'matches', 'list_name', ${d307})` |

Quando `${d307}` é igual a `"HF001"`, `search()` retorna todas as linhas em `externalData` onde `list_name = 'HF001'` — inteiramente a partir do arquivo incluído, sem chamada de rede.

### search() vs autocompletar rawquery

| Funcionalidade | `search()` | Autocompletar `rawquery` |
|---------|-----------|------------------------|
| Consultas SQL | Não — apenas igualdade de colunas | Sim — `SELECT … FROM …` completo |
| Entrada parametrizada | Correspondência de valor de coluna | Incorporado na string SQL |
| Entrada de texto livre | Sim — o enumerador pode digitar livremente | Não — deve selecionar da lista |
| UNION / multi-tabela | Não suportado | Suportado |

### Quando usar cada um

- Use **`search()`** quando precisar de uma correspondência de igualdade direta contra um arquivo `.db` incluído, o formulário deve funcionar offline e deseja permitir a entrada de texto livre.
- Use **autocompletar `rawquery`** quando precisar de flexibilidade SQL (JOINs, UNIONs, colunas calculadas) ou deve consultar várias tabelas, e o formulário tem conectividade confiável.

---

## Melhores Práticas

1. Garanta que o endpoint da sua API responda em 1–2 segundos — APIs lentas tornam a pesquisa pouco responsiva.
2. Use `%__input__%` no `post_body` para que a API retorne apenas os resultados correspondentes, não o conjunto de dados completo.
3. Indexe o campo de pesquisa no lado do servidor (ex: Elasticsearch, índice de texto completo do banco de dados) para respostas rápidas.
4. Limite os resultados a 20–50 itens por consulta — retornar milhares de resultados anula o propósito da pesquisa.
5. Inclua um requisito de comprimento mínimo de entrada na API para evitar acionar consultas amplas em entradas de um único caractere.

## Limitações

- A Pesquisa Dinâmica requer conectividade de rede — não funciona offline.
- O marcador `%__input__%` é injetado tal como está; sanitize as entradas no lado do servidor para evitar ataques de injeção.
- Expressões de exibição `@{func}` complexas podem ter suporte limitado em todas as versões do cliente rtSurvey.
