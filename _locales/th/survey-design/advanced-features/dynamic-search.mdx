---

**การค้นหาแบบไดนามิก** (หรือที่เรียกว่า Search API) ช่วยให้ฟิลด์ `select_one`, `select_multiple` หรือ `text` สามารถโหลดตัวเลือกจากบริการเว็บระยะไกล **ในขณะรันไทม์** เมื่อผู้จัดทำรายการพิมพ์ นี่เป็นแนวทางที่ถูกต้องเมื่อรายการตัวเลือกของคุณใหญ่เกินกว่าจะรวมไว้ในไฟล์ CSV มีการอัปเดตบ่อยครั้ง หรือมาจากฐานข้อมูลสด

---

## รูปแบบ `search-api()`

การค้นหาแบบไดนามิกได้รับการกำหนดค่าผ่านคอลัมน์ `appearance` โดยใช้ฟังก์ชัน `search-api()`:

```
search-api(method, url, post_body, value_column, display, data_path, save_path)
```

### พารามิเตอร์

| พารามิเตอร์ | คำอธิบาย |
|-----------|-------------|
| `method` | ใช้ `'POST'` เสมอ |
| `url` | เอ็นด์พอยต์ API ที่จะสืบค้น |
| `post_body` | เนื้อหา JSON ที่ส่งไปยัง API ใช้ `%__input__%` เป็นตัวแทนสำหรับข้อความค้นหาปัจจุบันของผู้จัดทำรายการ |
| `value_column` | คีย์ในอ็อบเจ็กต์ตอบกลับที่จะใช้เป็น **ค่า** (value) ที่จัดเก็บ |
| `display` | คีย์ (หรือเทมเพลต) ที่จะใช้เป็น **ป้ายกำกับ** (label) ที่แสดงในดรอปดาวน์ รองรับตัวแทน `##key##` และนิพจน์ `@{func}` |
| `data_path` | JSONPath ไปยังอาร์เรย์ของอ็อบเจ็กต์ผลลัพธ์ในการตอบกลับ (เช่น `$.data`, `$.hits.hits.*._source`) |
| `save_path` | ชื่อที่ใช้บันทึกการตอบกลับดิบเพื่อใช้โดยฟิลด์อื่น |

---

## ตัวอย่างพื้นฐาน

การค้นหาสถานพยาบาลที่ผู้จัดทำรายการพิมพ์ส่วนหนึ่งของชื่อสถานพยาบาล:

| type | name | label | appearance |
|------|------|-------|------------|
| select_one | facility | เลือกสถานพยาบาล | `search-api('POST', 'https://api.example.com/facilities/search', '{"query": "%__input__%"}', 'id', 'name', '$.results', 'facility_data')` |

API จะได้รับ `{"query": "nair"}` เมื่อผู้จัดทำรายการพิมพ์ "nair" และจะส่งคืน:

```json
{
  "results": [
    {"id": "HF001", "name": "Nairobi Central Clinic"},
    {"id": "HF002", "name": "Nairobi West Hospital"}
  ]
}
```

ดรอปดาวน์จะแสดง `Nairobi Central Clinic` และ `Nairobi West Hospital` โดยค่าที่จัดเก็บคือ `HF001` หรือ `HF002`

---

## การจัดรูปแบบการแสดงผลขั้นสูง

### การใช้เทมเพลต `##key##`

แสดงหลายฟิลด์ในป้ายกำกับ:

```
search-api('POST', 'https://api.example.com/search', '{"q": "%__input__%"}', 'id', '##name## (##district##)', '$.data', 'res')
```

แสดงเป็น: `Nairobi Central Clinic (Nairobi)`

### การใช้นิพจน์ `@{func}`

ใช้ตรรกะแบบมีเงื่อนไขในป้ายกำกับที่แสดง:

```
search-api('POST', 'https://api.example.com/search', '{"q": "%__input__%"}', 'id',
  '@{if_else(eq("##status##", "active"), "✓ ##name##", "✗ ##name##")}',
  '$.data', 'res')
```

ผลลัพธ์ที่ใช้งานอยู่จะแสดง `✓ Clinic Name` ส่วนที่ไม่ได้ใช้งานจะแสดง `✗ Clinic Name`

---

## การตั้งค่าค่าเริ่มต้น: `search-default-api()`

ใช้ `search-default-api()` หลัง `search-api()` เพื่อใส่ค่าเริ่มต้นในฟิลด์โดยโหลดจากการเรียก API แยกต่างหาก (เช่น เมื่อแก้ไขบันทึกที่มีอยู่):

```
appearance: search-api(...) search-default-api('POST', 'https://api.example.com/get', '{"id": "##saved_id##"}', 'id', 'name', '$.item')
```

---

## ตัวคั่นที่กำหนดเองสำหรับ select_multiple: `search-default-separator()`

สำหรับฟิลด์ `select_multiple` ให้ระบุวิธีเชื่อมค่าที่เลือกหลายค่าในสตริงที่จัดเก็บ:

```
appearance: search-api(...) search-default-separator(' || ')
```

ตัวคั่นเริ่มต้นคือช่องว่าง

---

## ประเภทคำถามที่รองรับ

| ประเภทคำถาม | กรณีการใช้งาน |
|---------------|----------|
| `select_one` | การเลือกรายการเดียวจากผลการค้นหา |
| `select_multiple` | การเลือกหลายรายการจากผลการค้นหา |
| `text` | เติมข้อความอัตโนมัติ — ผู้จัดทำรายการพิมพ์ได้อย่างอิสระแต่สามารถเลือกคำแนะนำได้ |

---

## การใช้ข้อมูลการตอบกลับที่บันทึกไว้

เมื่อผู้จัดทำรายการเลือกผลลัพธ์ rtSurvey จะบันทึกอ็อบเจ็กต์ที่ตรงกันทั้งหมดจากการตอบกลับภายใต้ชื่อ `save_path` ฟิลด์อื่นสามารถอ่านจากข้อมูลนี้ได้สองวิธี

### วิธีที่ 1 — การค้นหาด้วย `pulldata()`

ใช้ `pulldata('save_path', 'key')` เพื่ออ่านฟิลด์ระดับบนสุดจากอ็อบเจ็กต์ที่บันทึกไว้:

| type | name | label | calculation |
|------|------|-------|-------------|
| select_one | facility | เลือกสถานพยาบาล | |
| calculate | facility_district | | `pulldata('facility_data', 'district')` |
| calculate | facility_type | | `pulldata('facility_data', 'type')` |
| calculate | facility_beds | | `pulldata('facility_data', 'beds')` |

ลักษณะ (appearance) ในแถว `select_one` ต้องมี `search-api(..., 'facility_data')` ที่มี `save_path` ตรงกัน

สำหรับ **ฟิลด์ JSON แบบซ้อน** ให้ใช้ร่วมกับ `substr-jsonpath()`:

```
substr-jsonpath(pulldata('facility_data', 'location'), '$.district')
```

## การค้นหาไฟล์ในเครื่องด้วย search()

`search()` ทำการค้นหาความเท่ากันของคอลัมน์แบบออฟไลน์กับไฟล์ SQLite `.db` ที่รวมอยู่ด้วย — ไม่ต้องเชื่อมต่อเครือข่ายและไม่ต้องใช้แบบสอบถาม SQL ใช้เมื่อข้อมูลอ้างอิงของคุณถูกแพ็กมาพร้อมกับแบบฟอร์ม และคุณต้องการการค้นหาแบบง่ายๆ "ค้นหาแถวทั้งหมดที่คอลัมน์เท่ากับค่า"

### รูปแบบ (Signature)

```
search(path, 'matches', 'list_name', ${field})
```

### พารามิเตอร์

| พารามิเตอร์ | คำอธิบาย |
|-----------|-------------|
| `path` | เส้นทางไปยังตาราง SQLite: `concat(${family_path}, '/file.db::table')` |
| `'matches'` | ตัวดำเนินการจับคู่ — คืนค่าแถวที่คอลัมน์เท่ากับค่า |
| `'list_name'` | ชื่อคอลัมน์ที่ต้องการจับคู่ |
| `${field}` | ค่าที่ต้องการจับคู่ โดยปกติจะเป็นการอ้างอิงฟิลด์ |

### ตัวอย่าง

เติมข้อมูล `select_one` จากฐานข้อมูลในเครื่องโดยจับคู่ค่าของ `${d307}` กับคอลัมน์ `list_name` ในตาราง `externalData` ของ `d307.db`:

| type | name | label | appearance |
|------|------|-------|------------|
| select_one | facility | เลือกสถานพยาบาล | `search(concat(${family_path}, '/d307.db::externalData'), 'matches', 'list_name', ${d307})` |

เมื่อ `${d307}` เท่ากับ `"HF001"` ฟังก์ชัน `search()` จะคืนค่าทุกแถวใน `externalData` ที่ `list_name = 'HF001'` — ทั้งหมดมาจากไฟล์ที่รวมอยู่ด้วย โดยไม่มีการเรียกใช้เครือข่าย

### search() เทียบกับ rawquery autocomplete

| คุณสมบัติ | `search()` | `rawquery` autocomplete |
|---------|-----------|------------------------|
| แบบสอบถาม SQL | ไม่ — ความเท่ากันของคอลัมน์เท่านั้น | ใช่ — `SELECT … FROM …` แบบเต็ม |
| อินพุตที่มีพารามิเตอร์ | การจับคู่ค่าคอลัมน์ | ฝังอยู่ในสตริง SQL |
| การป้อนข้อความอิสระ | ใช่ — ผู้จัดทำรายการสามารถพิมพ์ได้อย่างอิสระ | ไม่ — ต้องเลือกจากรายการ |
| UNION / หลายตาราง | ไม่รองรับ | รองรับ |

### เมื่อใดควรใช้แต่ละอย่าง

- ใช้ **`search()`** เมื่อคุณต้องการการจับคู่ความเท่ากันที่ตรงไปตรงมากับไฟล์ `.db` ที่รวมอยู่ด้วย แบบฟอร์มต้องทำงานแบบออฟไลน์ และคุณต้องการอนุญาตให้ป้อนข้อความได้อย่างอิสระ
- ใช้ **`rawquery` autocomplete** เมื่อคุณต้องการความยืดหยุ่นของ SQL (JOIN, UNION, คอลัมน์จากการคำนวณ) หรือต้องค้นหาในหลายตาราง และแบบฟอร์มมีการเชื่อมต่อที่เชื่อถือได้

## แนวทางปฏิบัติที่ดีที่สุด

1. ตรวจสอบให้แน่ใจว่าเอ็นด์พอยต์ API ของคุณตอบสนองภายใน 1-2 วินาที — API ที่ช้าทำให้การค้นหารู้สึกไม่ตอบสนอง
2. ใช้ `%__input__%` ใน `post_body` เพื่อให้ API ส่งคืนเฉพาะผลลัพธ์ที่ตรงกัน ไม่ใช่ชุดข้อมูลทั้งหมด
3. จัดทำดัชนีฟิลด์การค้นหาที่ฝั่งเซิร์ฟเวอร์ (เช่น Elasticsearch, ดัชนีข้อความเต็มของฐานข้อมูล) เพื่อการตอบสนองที่รวดเร็ว
4. จำกัดผลลัพธ์ไว้ที่ 20-50 รายการต่อแบบสอบถาม — การส่งคืนผลลัพธ์หลายพันรายการทำให้จุดประสงค์ของการค้นหาเสียไป
5. กำหนดความยาวขั้นต่ำของอินพุตใน API เพื่อหลีกเลี่ยงการสืบค้นที่กว้างเกินไปเมื่อป้อนอักขระเพียงตัวเดียว

## ข้อจำกัด

- การค้นหาแบบไดนามิกต้องการการเชื่อมต่อเครือข่าย — ไม่สามารถทำงานแบบออฟไลน์ได้
- ตัวแทน `%__input__%` จะถูกแทรกตามที่เป็นอยู่ ควรทำความสะอาดข้อมูลอินพุตที่ฝั่งเซิร์ฟเวอร์เพื่อป้องกันการโจมตีแบบ Injection
- นิพจน์การแสดงผล `@{func}` ที่ซับซ้อนอาจมีการรองรับที่จำกัดในไคลเอนต์ rtSurvey บางเวอร์ชัน
